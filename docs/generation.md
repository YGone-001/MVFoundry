# AI Generation Jobs and Provider Adapters

This document covers the generation layer added in P1-E-C. It converts approved
production tasks into validated generation jobs, executes a fully offline
deterministic test provider, exposes one concrete Runway adapter that has **never
been executed live**, and hands generated bytes through the existing intake,
approval, compilation and rendering workflow.

It does not call paid providers, upload private references, transcribe audio or
generate real-song production assets.

## 1. Files in an external project

```
<project>/generation/
  jobs.json            versioned generation jobs
  permissions.json     per-job cost/network authorization records
  outputs/<jobId>/     raw provider output (offline fixture writes here)
  staging/<jobId>/     validated copy that intake points at
  manifests/<jobId>.json  result manifest (hash, probe, marker, provenance)
  fixtures/            recorded provider responses for simulated lifecycles
  reports/             generation report and simulation transcripts
```

All of it stays outside Git.

## 2. Job contract

A job is traceable to exactly one approved requirement and records: job id, project,
requirement id, storyboard revision, requirement fingerprint, shot ids, provider,
operation, model, request revision, compiled prompt, output spec, continuity ids and
revisions, input references, permission state, execution state, provider task id,
attempts, result files with hashes, failure detail, and review state.

`schemaVersion: 1`; states are split deliberately:

- permission: `not-requested`, `awaiting-authorization`, `authorized`, `denied`;
- execution: `prepared`, `awaiting-authorization`, `queued`, `submitted`, `running`,
  `succeeded`, `failed`, `canceled`, `unknown-submission-state`, `output-retrieved`;
- review: `awaiting-review`, `approved`, `rejected`.

A succeeded provider task is never an approved asset.

## 3. Identity, idempotency and retry safety

`GEN-<hash>-<revision>` is derived from project, requirement, storyboard revision,
requirement fingerprint, provider, model, operation, output spec, continuity ids and
input hashes. Re-preparing the same request returns the existing job
(`duplicate: true`) instead of creating a second one.

A timeout after submission parks the job as `unknown-submission-state` with no
provider task id. `resume` then refuses to submit again until the remote task is
reconciled, so an uncertain submission cannot be billed twice.

## 4. Continuity-aware prompt compilation

`compileGenerationPrompt` builds a structured section plus a human-readable draft from
the approved shot description, renderer/media slot, brief style, palette, setting,
camera and movement, continuity entries (with the approved revision), target
duration/aspect, exclusions and production constraints. It records
`includesLyrics: false`, `includesAudio: false`, `includesPrivatePaths: false`, and
refuses to emit a prompt containing a filesystem path. The draft separates
`supportedCapabilities` from `advisoryOnly`, and states that prompt wording cannot
guarantee visual identity consistency.

## 5. Provider contract

`GenerationProvider` exposes capabilities, `validate`, `submit`, `status`, `retrieve`
and an optional `cancel`. Capabilities declare operations, output kinds, models,
aspect ratios, durations, resolutions, reference limits, seed/alpha/audio support and
formats. `validateProviderRequest` rejects unsupported operations, models, output
kinds, ratios, durations, reference counts, seeds, alpha and unauthorized uploads
before anything is submitted.

## 6. Offline fixture provider

Provider id `offline-fixture`, model `offline-fixture-v1`. It writes real bytes:
PNG images, true RGBA layers with transparent surroundings, and H.264 MP4 clips with
known colour segments at the declared fps and frame count. Every output is marked
`synthetic-offline-test-output`. It never touches the network and only writes inside
`generation/outputs/<jobId>/`.

## 7. Runway adapter (not executed live)

Provider id `runway`, pinned to `X-Runway-Version: 2024-11-06`, implementing
`POST /v1/text_to_image`, `POST /v1/image_to_video`, `GET /v1/tasks/{id}` and output
retrieval. Model capability manifests: `gen4_image` (text-to-image) and `gen4_turbo`
(image-to-video, 5 s or 10 s clips, documented ratios).

The adapter takes an injected `HttpTransport`. There is no ambient `fetch` in this
path, and the default transport throws, so a live request cannot happen by accident.
The API key is read from `RUNWAY_API_KEY` only, is never written to a document, and
the recorded request transcript redacts the authorization header.

`LIVE RUNWAY GENERATION: NOT RUN — NOT AUTHORIZED`.

## 8. Permission gate

`checkGenerationPermission` fails closed when: the requirement fingerprint changed,
`permissions.allowNetwork` is false, credentials are missing for a live run, no
permission record exists, the record belongs to another job or mismatches
provider/model/operation, live execution lacks `authorized-live`, uploads were not
authorized, the submission cap is reached, or the provider/model/operation is
unsupported.

`generation approve-request` accepts only `authorized-for-simulation` or `denied` in
this phase; `authorized-live` is unavailable, and `submit-live` always fails with
`LIVE_PROVIDER_EXECUTION = NOT_GRANTED`.

## 9. Output pipeline

Staged output must live inside the project. The pipeline copies the bytes into
`generation/staging/<jobId>/`, computes SHA256, probes with `probeVideo` or
`probeLayerPng`, checks dimensions, codec, alpha and that the clip covers the shot,
writes a result manifest, and submits an **intake record with `review: "pending"`**
bound to the requirement fingerprint. Nothing is approved automatically.

Remote retrieval rules are documented for future adapters: HTTPS only, expected
hosts, reject loopback/link-local, validate redirect targets, enforce content-type,
size and timeout limits, never follow provider-returned local paths, and never trust
a URL extension as a type. Incompatible clips are rejected or explicitly derived with
the original retained and both hashes plus the FFmpeg parameters recorded; alpha is
never invented.

## 10. CLI

```text
npm run generation -- prepare --project <id> --requirement <REQ> [--provider offline-fixture|runway] [--model M] [--revision N] [--seed N]
npm run generation -- status --project <id> [--job <JOB>]        # exit 2 when a job is stale
npm run generation -- inspect --project <id> --job <JOB>
npm run generation -- approve-request --project <id> --job <JOB> --authorization <authorized-for-simulation|denied> --max-spend <usd> [--max-submissions N] [--uploads-private] --notes "<review>"
npm run generation -- run-offline --project <id> --job <JOB> [--rights "<rights>"]
npm run generation -- submit-live --project <id> --job <JOB>      # always refused in this phase
npm run generation -- resume --project <id> --job <JOB> --fixtures <project-relative.json>
npm run generation -- handoff --project <id> --job <JOB> --file <project-relative output> --rights "<rights>"
npm run generation -- review --project <id> --job <JOB> --decision <approve|reject> --notes "<review>"
npm run generation -- report --project <id>
```

Every command needs `--project` and `--workspace`/`MV_WORKSPACE_ROOT`. Exit 0 means
done, 1 means refused or failed, 2 means a guard reaction such as unsupported
capabilities or a stale job. No command approves anything implicitly.

## 11. Acceptance

`npm run generation:seed` creates `synthetic-generation-image-demo` (layered-canvas
image task), `synthetic-generation-video-demo` (video task plus a simulated Runway
lifecycle) and `synthetic-generation-continuity-demo` (two hybrid shots sharing
continuity). `npm run generation:verify` runs the whole lifecycle and decodes real
rendered output, including negative cases.

## 12. Limitations

- Offline output is deterministic synthetic media, not AI generation, and no live
  provider behaviour has been observed.
- The Runway contract and capability matrix were encoded from documentation and
  exercised only through an injected fake transport.
- Continuity is declarative; prompt wording cannot guarantee visual consistency.
- Remote URL retrieval and incompatible-clip normalization are specified and
  guarded but not exercised, because no live provider output exists in this phase.
